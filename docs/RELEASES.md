# فرایند به‌روزرسانی و انتشار فراهوش

این فرایند برای انتشار اصلاحات کوچک در طول سال تحصیلی و ارتقای نسخه‌های بزرگ‌تر طراحی شده است.

## ۱. پیش از شروع

- شاخه `main` و آخرین commit را بررسی کنید.
- یک شاخه مستقل با نام روشن بسازید؛ نمونه: `feature/attendance-approval` یا `fix/parent-report`.
- هدف، نقش‌های درگیر، صفحات، توابع، جدول‌ها و معیار پذیرش را در شرح کار ثبت کنید.
- قابلیت‌های سالم و خارج از محدوده را صریحاً مشخص کنید.
- از داده واقعی دانش‌آموزان در تست یا Pull Request استفاده نکنید.

## ۲. پیاده‌سازی

- تغییرات را کوچک و قابل مرور نگه دارید.
- اگر تغییر دیتابیس لازم است، migration جدید اضافه کنید و قبل از انتشار آن را در محیط آزمایشی بررسی کنید.
- اگر قرارداد تابع سمت سرور تغییر می‌کند، مصرف‌کنندگان آن را پیدا کنید و سازگاری نسخه قبلی را حفظ کنید.
- تغییرات رابط، API، دیتابیس و مجوزها را در یک Pull Request قابل فهم به هم مرتبط کنید.
- migration و کد برنامه باید با هم سازگار باشند؛ کد جدید نباید پیش از آماده بودن ساختار مورد نیاز منتشر شود.

## ۳. بررسی خودکار و دستی

پیش از ادغام:

1. workflowهای مرتبط GitHub Actions باید سبز باشند.
2. تست‌های موجود در `tests/` اجرا شوند.
3. برای تغییرات دیتابیس، اجرای migration روی محیط آزمایشی و بررسی RLS انجام شود.
4. برای تغییرات نقش‌ها، دسترسی نقش مجاز و عدم دسترسی نقش غیرمجاز هر دو آزموده شوند.
5. سناریوی اصلی کاربر از ابتدا تا انتها با حساب‌های آزمایشی اجرا شود.
6. نمایش موبایل، تاریخ شمسی و پیام خطا بررسی شوند.
7. diff نهایی از نظر فایل‌های خارج از محدوده، اطلاعات محرمانه و تغییر ناخواسته قابلیت‌های سالم بازبینی شود.

سبز شدن CI به تنهایی اثبات نمی‌کند که همه جریان‌های واقعی مدرسه درست کار می‌کنند؛ تست دستی سناریوهای اصلی نیز لازم است.

## ۴. انتشار و بازگشت

- ابتدا نسخه آزمایشی را با داده غیرواقعی و حساب‌های آزمایشی بررسی کنید.
- پیش از migration عملیاتی، از پایگاه داده پشتیبان قابل بازیابی تهیه و روش بازیابی را مشخص کنید.
- migrationهای افزایشی و سازگار را پیش از فعال کردن رابط جدید اجرا کنید.
- پس از انتشار، ورود نقش‌ها، فرم‌های اصلی، گزارش‌ها، ذخیره‌سازی فایل و دسترسی‌های حساس را بررسی کنید.
- اگر نسخه جدید مشکل دارد، در صورت امکان نسخه برنامه را به نسخه پایدار قبلی برگردانید. برای تغییرات دیتابیس، بازگشت باید بر اساس برنامه از پیش بررسی‌شده باشد؛ migration منتشرشده را دستی پاک یا بازنویسی نکنید.
- اصلاح فوری داده یا migration جدید باید ثبت و بازبینی شود.

## ۵. نسخه‌بندی و یادداشت تغییرات

- اصلاح کوچک و سازگار: نسخه اصلاحی؛ قابلیت افزایشی: نسخه فرعی؛ تغییر ناسازگار: نسخه اصلی جدید.
- هر انتشار باید تاریخ، خلاصه تغییرات، migrationهای افزوده‌شده، نیازهای تنظیمات و موارد قابل توجه را ثبت کند.
- قالب یادداشت‌ها در `CHANGELOG.md` قرار دارد.
- تا وقتی شماره نسخه رسمی و چرخه انتشار تثبیت نشده، شماره نسخه را از روی تاریخ یا نام commit حدس نزنید.

## ۶. چک‌لیست پایان انتشار

- [ ] Pull Request بازبینی و در شاخه اصلی ادغام شده است.
- [ ] workflowهای مرتبط موفق هستند.
- [ ] migrationها در محیط هدف اجرا و نتیجه بررسی شده است.
- [ ] پشتیبان و روش بازیابی مشخص است.
- [ ] نقش‌ها و RLS بررسی شده‌اند.
- [ ] سناریوهای اصلی با حساب آزمایشی موفق‌اند.
- [ ] قابلیت‌های خارج از محدوده بدون تغییر مانده‌اند.
- [ ] یادداشت انتشار به‌روز شده است.
