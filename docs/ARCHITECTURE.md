# معماری و توسعه‌پذیری فراهوش

این سند وضعیت معماری موجود را ثبت می‌کند و قواعدی را تعیین می‌کند که توسعه‌های بعدی، به‌ویژه به‌روزرسانی‌های بین سال تحصیلی، با کمترین ریسک انجام شوند.

## ۱. نقشه اجزای موجود

| بخش | مسیر | مسئولیت |
|---|---|---|
| صفحه ورودی | `index.html` | معرفی سامانه و انتخاب پنل |
| درگاه پنل‌ها | `portal.html` | انتخاب نقش و هدایت به قابلیت‌ها |
| صفحات عملیاتی وب | فایل‌های HTML ریشه و پوشه `classroom/` | رابط کاربری بخش‌های مدرسه |
| ابزارهای مشترک فعلی | `jalali-date.js`، `reports-utils.js` | تاریخ شمسی و توابع گزارش |
| توابع سمت سرور Supabase | `supabase/functions/` | عملیات کنترل‌شده سمت سرور |
| تغییرات دیتابیس Supabase | `supabase/migrations/` | نسخه‌بندی ساختار پایگاه داده |
| سرویس مستقل کلاس | `server/` | سرویس Node.js متصل به PostgreSQL مستقل |
| بسته مستقل کلاس | `standalone-classroom/` | فایل‌های رابط کلاس مستقل |
| آزمون‌ها | `tests/` | اعتبارسنجی ساختار، منطق و یکپارچگی |

**مرزبندی مهم داده‌ها:** توابع Supabase و سرویس مستقل کلاس دو مسیر اجرایی جدا هستند. وجود جدول یا تابع در یکی به معنی وجود یا همگام بودن آن در دیگری نیست. انتقال داده میان این دو فقط با طراحی صریح قرارداد، مجوز و سازوکار همگام‌سازی انجام شود.

## ۲. قواعد ماژولار بودن

- هر قابلیت جدید باید مالک مشخص داشته باشد: صفحه رابط، تابع سمت سرور، جداول و سیاست‌های دسترسی مربوط.
- منطق اختصاصی یک ماژول را در صفحه یا تابع ماژول‌های نامرتبط پخش نکنید.
- منطق واقعاً مشترک، مانند تاریخ شمسی یا قالب گزارش، باید در ابزار مشترک قرار گیرد؛ اما پیش از انتقال کد موجود، رفتار فعلی با تست تثبیت شود.
- نام عملیات، ورودی‌ها و خروجی‌های توابع سمت سرور باید روشن و مستند باشند.
- تغییرات قرارداد API تا حد امکان افزایشی و سازگار با نسخه قبلی باشند. حذف یا تغییر معنای یک فیلد موجود، تغییر ناسازگار محسوب می‌شود.
- قابلیت‌های بزرگ جدید ابتدا به صورت یک برش کوچکِ کامل از رابط تا ذخیره‌سازی و کنترل دسترسی پیاده‌سازی شوند؛ سپس توسعه یابند.

## ۳. قواعد پایگاه داده و migration

1. برای هر تغییر ساختاری، یک migration جدید با نام زمان‌دار و توضیح روشن بسازید؛ فایل migration منتشرشده را ویرایش نکنید.
2. migration باید قابل بازبینی، محدود به نیاز همان قابلیت و تا حد ممکن تکرارپذیر باشد.
3. قبل از تغییر ستون یا جدول موجود، تمام مصرف‌کنندگان آن را در صفحات، توابع و گزارش‌ها پیدا کنید.
4. تغییر ناسازگار را در چند مرحله انجام دهید: ابتدا ستون یا قرارداد جدید را اضافه کنید، برنامه را با هر دو حالت سازگار نگه دارید، داده را منتقل و اعتبارسنجی کنید، سپس حذف ساختار قدیمی را در انتشار جداگانه بررسی کنید.
5. migrationهای مخرب مانند حذف جدول، حذف ستون یا پاک‌سازی داده بدون پشتیبان معتبر و برنامه بازگشت اجرا نشوند.
6. سیاست‌های RLS، نقش‌ها، مجوزهای جدول و دسترسی Storage همراه migration بررسی شوند؛ صرف ایجاد جدول کافی نیست.
7. برای داده‌های حساس دانش‌آموزان، دسترسی باید بر اساس نقش و رابطه مجاز با دانش‌آموز محدود باشد.

## ۴. امنیت و تنظیمات محیط

- هیچ رمز، توکن، کلید خصوصی یا service-role key در فایل‌های HTML، کد مرورگر، تست یا مخزن ثبت نشود.
- تنظیمات محیط توسعه، آزمایشی و عملیاتی از هم جدا باشند.
- کلید عمومی قابل استفاده در مرورگر نیز باید فقط همراه سیاست‌های درست RLS و مجوزهای محدود استفاده شود.
- عملیات حساس با نقش کاربر به تنهایی مجاز نمی‌شوند؛ سمت سرور باید هویت، نقش و محدوده دسترسی را بررسی کند.
- برای هر تغییر در دسترسی، آزمون مثبت و منفی لازم است: کاربر مجاز باید موفق شود و کاربر غیرمجاز باید رد شود.
- لاگ‌ها نباید رمز، توکن نشست، شناسه‌های حساس یا محتوای محرمانه پرونده دانش‌آموز را افشا کنند.

## ۵. تاریخ، زبان و سازگاری رابط

- رابط کاربری فارسی و راست‌به‌چپ باقی بماند.
- تاریخ نمایشی در صفحات مدرسه باید با ابزار تاریخ شمسی موجود هماهنگ باشد.
- زمان ذخیره‌شده در پایگاه داده باید دارای منطقه زمانی/استاندارد روشن باشد؛ تبدیل به تاریخ شمسی در لایه نمایش انجام شود.
- پیش از تغییر ابزار تاریخ، تست‌های `tests/validate-jalali-dates.mjs` اجرا شوند.
- در تغییرات رابط، نمایش موبایل و صفحه‌نمایش کوچک نیز بررسی شود.

## ۶. مرزهای حساس و قابلیت‌های سالم

سرویس مستقل کلاس و فایل‌های مربوط به آن مرزهای حساس معماری‌اند. تغییر در `server/`، `classroom/`، `standalone-classroom/` یا توابع `classroom-*` باید فقط وقتی انجام شود که خود قابلیت کلاس در محدوده درخواست باشد و تست اختصاصی آن نیز آماده باشد.

درخواست توسعه یک ماژول دیگر، مجوز بازنویسی یا تغییر رفتار کلاس آنلاین، آزمون آنلاین یا ملاقات‌ها نیست. در صورت نیاز به تغییر قرارداد مشترک، ابتدا اثر آن و آزمون رگرسیون باید مشخص شود.

## ۷. معیار آماده بودن یک قابلیت

یک قابلیت زمانی آماده انتشار است که:

- مسیر کاربر و نقش‌های مجاز مشخص باشند؛
- فرم و جدول واقعاً به منبع داده متصل باشند و داده آزمایشی ساختگی جای داده واقعی را نگرفته باشد؛
- ثبت، مشاهده، ویرایش و حذف فقط در صورت نیاز همان قابلیت پیاده‌سازی و آزموده شده باشند؛
- خطاهای شبکه و مجوز به کاربر پیام قابل فهم بدهند؛
- RLS و کنترل سمت سرور بررسی شده باشند؛
- تاریخ، زبان و نمایش موبایل بررسی شده باشند؛
- تست‌های مرتبط و مرور diff موفق باشند؛
- راهنمای کاربری یا یادداشت انتشار به‌روز شده باشد.

## ۸. مسیر توسعه آتی

برای رشد سامانه، قابلیت‌های جدید به ترتیب وابستگی اضافه شوند: تثبیت هویت و مجوزها، تکمیل جریان داده هر ماژول، گزارش‌های یکپارچه، اعلان‌ها و گردش تأیید، سپس امکانات هوشمند و اتصال‌های بیرونی. اتصال به سامانه‌های بیرونی فقط از مسیر رسمی و مجاز و با قرارداد API یا خروجی داده مجاز انجام شود.
