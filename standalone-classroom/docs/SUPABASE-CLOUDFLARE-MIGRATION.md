# فراهوش: قرارداد مهاجرت Supabase + Cloudflare

وضعیت: طرح اجرایی؛ این سند به‌تنهایی به معنی تکمیل مهاجرت نیست.

## تصمیم معماری

- **Supabase Auth** منبع اصلی احراز هویت کارکنان و دانش‌آموزان است. برای ورود با نام کاربری از تابع موجود `login-by-username` در مخزن اصلی استفاده می‌شود؛ حساب‌ها نباید صرفاً برای مهاجرت دوباره ساخته یا رمزهایشان بازنشانی شوند.
- **Supabase Database** منبع اصلی نقش‌ها، انتساب‌های آموزشی و برنامه هفتگی/روزانه است. هر درخواست باید تحت RLS یا یک لایهٔ سروری با حداقل دسترسی مجاز شود.
- **Cloudflare Workers** لایهٔ اتاق و کنترل جلسه است: شروع/پایان، اعتبارسنجی کلاس فعال، نقش، دبیر منصوب‌شده، کلاس دانش‌آموز و زمان جلسه.
- **Cloudflare Realtime** باید برای رسانه/ارتباط زنده پس از بررسی تناسب محصول و اثبات فنی انتخاب شود. صرفاً میزبانی Worker به معنی انتقال صوت و تصویر نیست.
- **D1** در دورهٔ گذار فقط برای وضعیت عملیاتی کلاس/رویدادهایی که نیازمند ذخیره محلی Worker هستند باقی می‌ماند؛ نباید منبع دوم و متناقض حساب یا برنامه هفتگی شود.

## محدودیت‌های مهاجرت

1. ابتدا قرارداد دادهٔ واقعی Supabase (جداول، ستون‌ها، RPCها و سیاست‌های RLS) بررسی شود. نام ستون یا نقش از روی حدس ساخته نشود.
2. توکن Supabase باید در سمت سرور اعتبارسنجی شود؛ decode کردن JWT بدون بررسی امضا کافی نیست.
3. شناسهٔ کاربر Supabase به شناسهٔ محلی D1 فقط از طریق نگاشت صریح و پایدار وصل شود؛ تطبیق صرفاً با نام نمایشی مجاز نیست.
4. هیچ حساب، رمز، جدول یا داده‌ای به‌صورت خودکار حذف، بازنشانی یا overwrite نشود.
5. کلید service-role/secret فقط در secrets سمت سرور قرار گیرد و هرگز به مرورگر، فایل ثابت یا APK فرستاده نشود.
6. پیام خطای کاربر عمومی باشد؛ جزئیات مرحلهٔ خطا در لاگ بدون رمز، توکن، کد ملی یا دادهٔ شخصی ثبت شود.
7. انتقال رسانه باید مستقل از ورود و برنامه آزمایش شود. PeerJS عمومی تا زمانی که مسیر جایگزین روی دو دستگاه و دو شبکه موفق نشده، ناگهان حذف نشود.

## ترتیب پیاده‌سازی و معیار خروج

### مرحله 1 — شناخت قرارداد و آزمون پایه
- ثبت schema واقعی Supabase و قرارداد ورود موجود.
- آزمون‌های ورود، نقش، برنامه، شروع/پایان و دسترسی غیرمجاز.
- ثبت وضعیت فعلی و حفظ شاخهٔ اصلی.

### مرحله 2 — هویت Supabase
- ورود با جریان فعلی `login-by-username`.
- اعتبارسنجی نشست و نگاشت role/profile.
- حفظ حساب‌ها و رمزهای موجود.
- آزمون واقعی مدیر، معاون، دبیر و دانش‌آموز؛ پاسخ HTTP موفق به‌تنهایی کافی نیست.

### مرحله 3 — برنامه و مجوز
- خواندن برنامه دبیر/دانش‌آموز از Supabase.
- شروع کلاس فقط برای دبیر منصوب‌شده و زمان مجاز.
- ورود دانش‌آموز فقط به کلاس خودش و پس از فعال‌شدن جلسه.
- آزمون دسترسی مستقیم API، نه فقط مخفی‌بودن دکمه‌ها در UI.

### مرحله 4 — ارتباط زنده
- انتخاب محصول/مسیر رسانه Cloudflare مناسب و مستندکردن محدودیت‌ها.
- پیاده‌سازی اتصال، مجوزهای میکروفن/دوربین، پیام‌رسانی و تخته.
- آزمون قطع‌و‌وصل شبکه، چند شرکت‌کننده و پایان جلسه.

### مرحله 5 — انتشار
- CI سبز، آزمون end-to-end واقعی، بازبینی امنیت و گزارش صریح موارد ناتمام.
- تا پیش از گذراندن این معیارها، نسخه برای استفادهٔ رسمی مدرسه آماده اعلام نشود.
